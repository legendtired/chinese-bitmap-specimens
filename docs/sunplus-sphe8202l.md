# Sunplus SPHE8202L 简体点阵

本次只新增 `CP936` 未压缩对象的 **16×16、20×24** 两款简体字样。12×12 与已有 HZK12 的全部 7,445 个标准 GB2312 字符（含 6,763 汉字）在完整字框中逐像素相同，合并为已有设计的来源说明，**不新增目录项、不改动原 HZK12 条目**。源归档中的繁体对象不纳入目录、预览或提取器。

下文仍记录三个已核简体源对象，用于完整技术对照。它们直接读取预先存储的单色位图，不执行设备固件，不进行矢量栅格化、缩放、平滑、补字或跨字库配字。

证据确认的是**原生位图存储**。尚无原厂设计资料证明其最初是逐点手绘、从轮廓生成或经过何种人工调校，不能由二进制储存形式反推制作历史。

- 16×16：`ccde5faca1424eeb8b6c32d6d33142910146fa8952e134c22beaffa0df84eae2`
- 20×24：`26c367d39cf2d0eb39d926337b453ac87400f37b3c58d001efdd518d8da3db2e`

- 12×12：`e6135cbfde217794148394c379699f9795dc9d9cae6d14e43be57442a8a7e61a`
- 16×16：`1f0ad632938ced219964358f11aa78fed84da5578eca4383182289ec724f32a8`
- 20×24：`3092173e88303e04a9c29c9f3deb4212557beeba8de63f0ee603f5b4e25103e4`

源对象为 ELF32、小端、MIPS 可重定位对象。三款符号均从 `.rodata` 开始，段末另有 **2 个零字节用于对齐**，不是字模。提取器先校验完整归档，再检查 GNU ar 长文件名表、成员边界、对象 SHA、ELF 节表、符号类型和符号长度，最后校验字模符号 SHA。

符号头是宽、高，后面每字的位连续排列，按行从左到右、每字节高位在前。**12 和 20 位宽的源数据没有逐行补齐到字节**，两行之间可能共用一个字节；不能直接按 2 或 3 字节一行读源文件。BDF 输出需要逐行补零，其补零规则与源格式分开处理。

## 字框、墨迹及 ASCII

| 项目 | 12×12 | 16×16 | 20×24 |
| --- | ---: | ---: | ---: |
| 原始存储字框 | 12×12 | 16×16 | 20×24 |
| 6,763 汉字的最大墨迹宽／高 | 12×12 | 16×14 | 20×21 |
| 固定句 PNG | 155×12（仅本地对照） | 203×16 | 251×24 |
| 标准映射中非空字符数 | 7,444 | 7,443 | 7,442 |

固定句为“视野无限广，窗外有蓝天。”，全部来自对应 CP936 对象，保持完整存储框；每字间附加 1px 仅为样图排版间隔。不会裁掉原始留白，也不把墨迹高度当成字框高度。提取器另可生成“片版牌局”固定诊断图。

三对象都**没有独立的一字节半角 ASCII 字模**。原归档另有西文字体对象及 ASCII 转换规则，但未核实设备的具体配对关系，本次不使用它们、不借字，也不把全角字形当成半角。两条新增网站字样省略整空 ASCII 行，元数据明确 `asciiOrigin=absent` 并列出 U+0020–U+007E 的 95 个缺失码位。这只描述所选对象，不是宣称整个归档没有西文字体。

## 原码覆盖与标准 Unicode 解释

`FontInfo_FONT_CP_936.o` 的原始范围表给出：高字节 A1–A9、B0–F7，低字节 A1–FE。物理上是 **7,614 个槽**，其中 **7,445 个标准 GB2312 已赋码字符**，含全部 **6,763 个汉字**。三款的 6,763 汉字都不为空。

对象虽然名为 CP936，实际存储及本次导出范围不是完整 GBK。提取器按**原 GB2312 物理码位→标准 Unicode**解释，而不是对整段字节直接使用 Python `gbk` 或 `cp936`。改用 `gbk` 会额外把 33 个原 GB2312 未定义槽赋码，并改动以下两个标签，不能静默混用：

| 原码／物理槽 | 本次标准 GB2312 标签 | Python GBK 标签 | 原运行时表证据 |
| --- | --- | --- | --- |
| A1A4／3 | U+30FB | U+00B7 | U+30FB→A1A4；U+00B7→A1F5 |
| A1AA／9 | U+2015 | U+2014 | U+2015→A1AA；U+2014→A1F5 |

两处标签均保留标准 GB2312 解释，也由原表支持。不额外补同形别名。169 个未赋码物理槽仍做逐位审计，但不猜 Unicode、不加入 BDF。

映射字符中，12×12 的 U+3000 为空；16×16 另有 U+02C9 为空；20×24 再有 U+FF3F 为空。原始空白照样保留，不用其他字体补上。因此“全 6,763 汉字非空”不能扩大为“全 7,445 字符都有墨迹”。

### 与原运行时近似转换器的区别

原包还包含 `Unicode→GB2312` 转换器。它有繁转简、近似替换及重复别名，并不是“每个物理字模唯一对应哪个 Unicode”的反向表。直接重演它会把某些标准码位转到另一个槽，使原槽字形丢失。本次**不修改或纠正原转换器，也不复刻它**；保留原 GB2312 槽的标准 Unicode 解释，固定样句不受这些差异影响。

原 `FontInfo_FONT_CP_936.o` 为 52,428 字节，SHA-256：

`bdbe34c290c34a73dcc6fb063172218dac10847cae84189674177a26d7383477`

- `UtoG`：44,506 字节，SHA `8ada71afbea4af69cfebed861481b1839faf3c4f434e9cb4a785e4119f561ad4`

## 本地重绘及可选 BDF

需要 Python 3.9+，仅使用标准库。自行取得并确认有权处理匹配 SHA 的归档，放在被忽略的 `local-research/` 下。输入仅作数据读取，不执行源库或固件，也不联网。

```sh
python3 scripts/sunplus_bitmap_export.py local-research/sunplus/libfont.a \
  --output local-research/generated/sunplus
```

默认生成三个源对象的原尺寸固定句 PNG、固定诊断 PNG 及不含字模的聚合报告。这是**三个本地技术对照输出，不是三个新增目录项**；12×12 已确认为现有 HZK12 的重复字形。可用 `--size 12x12`、`--size 16x16` 或 `--size 20x24` 限定一款。没有繁体参数或任意对象导出模式。

如有相应使用权，需要本地 BDF 时显式添加：

```sh
python3 scripts/sunplus_bitmap_export.py local-research/sunplus/libfont.a \
  --output local-research/generated/sunplus-bdf --export-bdf
```

文件名带 `-gb2312-standard-unicode-interpretation.bdf`，BDF COMMENT 也明确 **standard Unicode interpretation**：是原 GB2312 槽的标准 Unicode 解释，不是原运行时近似转换器的复刻。每款保留 7,445 个标准赋码字符，不补 ASCII、不扩展 GBK、不增加别名，不公开完整输出。

BDF 用 `BBX width height 0 0`、`DWIDTH width`、ascent=height、descent=0 展开完整存储框。`SIZE height 75 75` 对应 12／16 点 `SWIDTH 960`、20×24 的 `SWIDTH 800`。这些是**显式的上对齐字框导出约定，不是已知实机 advance 或基线**。BDF 每行左对齐并在右侧补到完整字节，12／20 位宽各补 4 个零位，源像素不变。

已有任一目标文件时整批拒绝覆盖。输入与输出目录不接受符号链接；不提供 force、联网下载或执行设备程序的选项。

```sh
python3 tests/sunplus.test.py
SUNPLUS_LIBFONT=local-research/sunplus/libfont.a python3 tests/sunplus.test.py
python3 scripts/verify_sunplus_bitmap_decode.py local-research/sunplus/libfont.a \
  --specimen-dir assets/specimens --report local-research/sunplus-independent-audit.json
```

公开测试使用合成 ar／ELF、合成点阵，检查容器边界、跨字节行位序、BDF 补位／度量、PNG、输入 SHA、符号链接及拒绝覆盖；不嵌入原始字模。没有私有输入时源文件核验明确跳过，不冒称已经核过实际库。

独立验证器重新解析 ar 与 ELF，不用被测提取器生成参考像素；按逐字节逐位寻址核对三个源对象全部 **22,842 个物理槽、6,700,320 个源像素**。另独立枚举全部 GB2312 源槽，核对各 7,445 字 BDF 内存回读、全部 6,763 非空汉字，以及 PNG 的 CRC、每个像素、间隔和尺寸；`--specimen-dir` 只要求两张正式16／20×24样图，12点仍在内存中作源对照。FontInfo 的符号边界、22 段映射及上述 24 处差异也单独核对。报告只含计数、哈希与状态，不含完整字模。

## 查重边界

目录固定图筛查不要求字形外围有一圈额外空白，避免邻字接触时漏报。对收录前227项筛查，12×12与已有 HZK12 的10字样句全部匹配；16×16、20×24未出现同样命中。固定图的图案筛查不是所有历史字体的同码位全库比较。

随后从原始 HZK12 二进制（196,272字节，SHA `d83b7f1603e87dd68bebc3a6a159c57909779684188cba790146f59424c28a02`）按相同GB2312原码读取，Sunplus12的 **7,445／7,445 字符、6,763／6,763 汉字**全部完整12×12像素相同，无裁白、平移或缩放。因此12点不单列新款。HZK12另存有其他槽位，不能把共同字符全同扩大为两份完整二进制文件相同。

另与可取得的 HZK16、Beijing16、HZK24 宋／黑／楷／仿宋、Windows 3.2 宋体13／16／20／24、已排除 ALi24／MStar24，以及已撤 Solaris12／14／20、已撤 /efont/、国乔15、ETen16／24、GuoBiao／ISAS、NISC 作共有汉字全量裁白边比较。各次共有字数不同，详见聚合审计；16／20×24在这些参考中未见整库完全相同。此结论不包含已确认与HZK12重复的12点。

16×16、20×24 另做固定样字最近邻缩放及单像素扩展模型筛查，未得到精确匹配。该有限模型不排除其他历史缩放、轮廓生成或手工修改方法；精确相同数量低也不等于已证明原创、无近似关系或手绘。

中国版 PS2 24×24 另补查14个汉字：先以完整 ROM2 的固定 SHA 核对原像素，再分别使用整24×24框及裁白字面，按记录的宽高范围作最近邻变换，以及单像素横向／纵向扩展。5,040 次重采样对应 15,120 次位图比较，未精确匹配 Sunplus16 或20×24 样字。结果限于这些明确模型，不是排除所有衍生设计的证明。

另补11个新恢复历史来源：Taipei s／b／r 24、Taipei b／k／l／m／r／s 20、cch24、ccic Taipei Li24。两款合计101,186对共有汉字作裁白不缩放比较，精确相同0；其中5个24点源另逐24,295个共有汉字作整框24→20×24最近邻横压，精确相同0。样字范围变换与单像素横／纵扩展另有123,120次位图比较，未精确匹配。旧转换BDF中的 `ENCODING -1` 不当作Unicode字形，ccic Taipei Li24改用核SHA的原始Big5 BDF；Big5双码同Unicode的“十／卅”采用可编码往返的标准原码，未让别码覆盖同一Unicode记录。完整源仍仅用于私有研究。
